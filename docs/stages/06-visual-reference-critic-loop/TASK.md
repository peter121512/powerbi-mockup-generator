# Stage 06 — Visual Reference Generation and Headless Screenshot Critic Loop

## Context

Stages 01–05c have established a working end-to-end pipeline:

```text
Natural-language requirement
    ↓
AI dashboard designer
    ↓
validated DashboardSpec
    ↓
coherent synthetic data
    ↓
PBIP/TMDL/PBIR renderer
    ↓
Fabric deployment
    ↓
populated semantic model + working DAX
    ↓
report opens and renders in browser
```

The original product ambition was not merely to create a functional Power BI report. It was to create a dashboard that feels genuinely premium, enterprise-grade, and credible in front of senior executives.

Earlier static image mockups generated by ChatGPT/image models demonstrated a substantially higher visual bar than the current mechanically rendered report. This stage introduces a deliberate visual-target and critic loop to close that gap.

The guiding idea is:

> Use a strong image-generation model to create a target-state visual reference from the same analytical/design intent, then compare the actual rendered Fabric screenshot against that target and the canonical DashboardSpec. Convert the gap into structured, implementable revisions.

The image is a **visual oracle/reference**, not an executable specification and not a source of truth for data semantics.

## Current OpenAI model guidance

As of August 2026, OpenAI's current API documentation lists:

- `gpt-image-2` as the current flagship image-generation model;
- GPT-5.6 Sol as the frontier model for complex professional reasoning and multimodal analysis.

Use these as the preferred defaults **only after verifying current availability in the configured OpenAI account at implementation time**. Model names must be configurable and must not be scattered through domain code.

If a newer/better generally available image or multimodal reasoning model exists when this stage is implemented, prefer it and document the choice.

## Stage objective

Build and prove the first **visual reference + headless screenshot critic loop** for the Executive Overview page.

Conceptually:

```text
User requirement + DashboardSpec
    ↓
Visual reference generator
    ↓
REFERENCE.png

Deployed Fabric report
    ↓
headless embedded renderer
    ↓
ACTUAL.png

DashboardSpec + REFERENCE.png + ACTUAL.png
    ↓
multimodal visual critic
    ↓
structured VisualCritique
    ↓
revision planner
    ↓
small targeted spec/renderer changes
    ↓
redeploy
    ↓
new screenshot
    ↓
re-score / stop
```

This stage should complete **at least one real refinement iteration** on the live retail Executive Overview.

## Critical architectural principle

Keep three concepts separate:

1. **Analytical truth** — owned by `DashboardSpec` and the semantic model.
2. **Desired visual outcome** — represented by the generated reference image.
3. **Actual implementation** — represented by PBIR/Power BI rendered output.

The reference image may suggest visual treatments that Power BI cannot reproduce exactly. The critic/revision system must distinguish:

- designer/spec deficiencies;
- renderer/formatting deficiencies;
- Power BI platform limitations;
- non-actionable differences caused by image-model fantasy.

Never let the image model silently redefine KPIs, measures, page purpose or data semantics.

## Required capabilities

### 1. Visual reference generation service

Create a narrow service that accepts at minimum:

- original user requirement;
- canonical `DashboardSpec`;
- selected page ID;
- optional existing theme/design-system context;

and generates a polished static reference image for that page.

Conceptual API:

```python
generate_visual_reference(
    requirement: str,
    spec: DashboardSpec,
    page_id: str,
    output_path: Path,
) -> VisualReferenceResult
```

Use the current strongest practical OpenAI image-generation model, preferably `gpt-image-2` if still current/available.

### 2. Reference prompt construction

Do not send the image model a vague prompt such as "make a beautiful dashboard".

Build a disciplined reference prompt from structured information including:

- page role and audience;
- analytical questions;
- KPI names and hierarchy;
- required visual types/analytical tasks;
- page layout intent;
- theme and colour roles;
- typography/design intent;
- business narrative;
- executive/boardroom quality bar;
- explicit instruction not to invent extra KPIs or materially alter the analytical content.

The reference should aim for visual quality while remaining implementable in mainstream Power BI.

Explicitly discourage:

- impossible 3D UI;
- decorative illustration unrelated to analysis;
- non-Power-BI-like controls;
- tiny unreadable text;
- excessive glassmorphism/neon/consumer-app styling;
- fake charts with nonsensical labels;
- extra metrics not present in the spec.

### 3. Reference image artefact

For the live fixture, generate and persist:

`docs/stages/06-visual-reference-critic-loop/reference-executive-overview.png`

If image artefacts are too large for normal repo practice, store them through the project's chosen artifact mechanism and commit a manifest/reference instead.

The report must document the exact model and high-level prompt approach used.

### 4. Headless screenshot architecture

Implement a screenshot path that does **not** rely on an already-open desktop browser profile or interactive OS session.

Preferred architecture:

```text
service/app credential
    ↓
Power BI/Fabric embed configuration/token
    ↓
minimal local/temporary embed HTML
    ↓
headless Chromium (Playwright)
    ↓
Power BI JS SDK rendered event
    ↓
page screenshot
```

The goal is to make screenshot capture suitable for future CI/server execution.

### 5. Non-interactive authentication

Investigate the existing tenant/workspace capabilities and implement the simplest safe non-interactive route available.

Potential routes include:

- service principal / app registration + Power BI embed token;
- service principal with supported report access;
- another official Fabric/Power BI embedding flow.

Requirements:

- no reuse of a locked personal Edge profile;
- no human login required during normal automated capture;
- no credentials/tokens persisted in Git;
- token lifetime handled safely;
- authentication isolated behind a small provider/broker abstraction.

If tenant settings or permissions block this, document the exact required admin action and continue all non-blocked work. Do not fall back to fragile desktop automation as the target architecture.

### 6. Embedded report host

Create the minimum required HTML/JS host page or equivalent runtime to embed the deployed report with the Power BI JavaScript client.

Requirements:

- configurable workspace/report/page target;
- hidden/minimal browser chrome;
- fixed viewport matching intended report canvas/aspect ratio;
- wait for Power BI `loaded` and `rendered` events rather than arbitrary sleeps where possible;
- configurable timeout;
- capture console/network errors for diagnostics;
- deterministic page selection.

### 7. Headless capture service

Provide a public capture function conceptually similar to:

```python
capture_report_page(
    report_id: str,
    page_name: str,
    output_path: Path,
) -> ScreenshotResult
```

Use headless Chromium/Playwright.

The capture result should distinguish:

- success;
- auth/embed failure;
- report load timeout;
- visual render timeout;
- browser/runtime failure.

### 8. Screenshot cleanliness

The captured image should contain the report canvas only, not irrelevant Fabric navigation/account UI.

Aim for stable dimensions and no scrollbars.

Store the first actual screenshot as:

`docs/stages/06-visual-reference-critic-loop/actual-before.png`

and the post-refinement screenshot as:

`docs/stages/06-visual-reference-critic-loop/actual-after.png`

### 9. Multimodal visual critic

Implement a visual critic using a strong current OpenAI multimodal reasoning model, preferably GPT-5.6 Sol if still current/available.

Inputs:

- `DashboardSpec` page content;
- original requirement;
- generated reference image;
- actual Fabric screenshot.

Output must be **structured**, not free-form prose.

Create a typed model such as `VisualCritique` containing dimensions like:

- overall score;
- executive credibility;
- information hierarchy;
- visual density;
- whitespace;
- alignment/grid discipline;
- KPI prominence;
- typography/readability;
- colour/theme consistency;
- chart appropriateness;
- chart legibility;
- slicer/filter placement;
- data storytelling;
- polish/premium feel;
- reference fidelity;
- implementation feasibility.

For each issue capture:

- severity;
- page/visual target;
- observed problem;
- expected/desired state;
- likely owner (`designer`, `renderer`, `theme`, `layout`, `powerbi_limit`, `non_actionable_reference_gap`);
- recommended concrete action;
- confidence.

### 10. Critic must judge against both target and purpose

The critic must **not** simply optimize pixel similarity to the reference image.

It should ask:

- Does the actual dashboard achieve the analytical purpose?
- Is the hierarchy appropriate for the CEO/CFO audience?
- Is the reference itself proposing anything impractical or analytically inferior?
- Which differences matter to perceived quality?

A difference can be acceptable even when the images do not visually match exactly.

### 11. Reference feasibility classification

For every major gap between reference and actual, classify whether it is:

- directly achievable with existing renderer capabilities;
- achievable with a small renderer extension;
- achievable through spec/layout/theme amendment;
- difficult/unreliable in native Power BI;
- purely decorative/non-essential;
- analytically undesirable despite looking attractive.

This prevents the system chasing impossible image-model artefacts.

### 12. Revision planner

Add a deterministic/structured revision-planning layer that converts critic findings into an ordered set of implementable changes.

Do not let the vision model directly edit arbitrary PBIR JSON.

Conceptually:

```text
VisualCritique
    ↓
RevisionPlan
    ├── spec amendments
    ├── renderer formatting amendments
    ├── layout amendments
    └── deferred/platform-limited items
```

Changes should be small and attributable.

### 13. First automatic refinement iteration

For the live Executive Overview, perform at least one complete cycle:

1. generate reference image;
2. capture current actual screenshot;
3. critique;
4. create revision plan;
5. apply the highest-value safe changes;
6. rerender/redeploy;
7. capture new screenshot;
8. re-run critic;
9. compare scores/issues before vs after.

Do not simply hand-edit the fixture to manufacture improvement. Changes should improve the general renderer/spec pipeline.

### 14. Stopping policy

Implement an explicit loop policy suitable for future automation.

Default maximum: **3 iterations**.

Stop early if:

- no critical/high-severity actionable issues remain;
- improvement score gain falls below a sensible threshold;
- remaining gaps are classified as Power BI limitations/non-actionable;
- a change would risk analytical correctness.

Do not allow an unbounded autonomous visual loop.

### 15. Score interpretation

The score is a development heuristic, not objective truth.

Do not optimize a single scalar blindly. Preserve issue-level evidence and require no regression on:

- analytical correctness;
- measure correctness;
- visual completeness;
- report loadability;
- data/model integrity.

### 16. Regression guardrails

After every refinement iteration verify:

- report still deploys through the working Stage 05c split deployment path;
- Executive Overview still renders;
- all source visuals remain present unless an explicit spec revision intentionally changes them;
- semantic model refresh remains successful;
- critical measures still evaluate;
- no visual overlaps/out-of-canvas errors introduced;
- automated tests remain green.

### 17. Image/model provider abstraction

Keep image generation and multimodal critique behind small provider abstractions.

Do not hard-wire OpenAI request code throughout the pipeline.

Conceptually:

```text
VisualReferenceProvider
VisualCriticProvider
```

One concrete OpenAI implementation each is sufficient for this stage.

### 18. Cost/runtime diagnostics

Record lightweight diagnostics for each model call:

- model;
- elapsed time;
- image dimensions;
- token/usage information when available;
- iteration count;
- final score delta.

Do not build a billing system.

### 19. Live Stage 06 manifest

Commit `VISUAL_LOOP_MANIFEST.json` with non-sensitive information including:

- reference model;
- critic model;
- report/page IDs/names where safe;
- reference image path;
- before screenshot path;
- after screenshot path;
- initial critique score/dimensions;
- final critique score/dimensions;
- issues fixed;
- deferred issues;
- iteration count;
- deployment outcome;
- screenshot outcome.

## Executive Overview quality target

The reference and critic should aim for an Executive Overview that feels appropriate to a CEO/CFO board-level discussion.

Desirable characteristics:

- immediate understanding of business performance;
- clear KPI hierarchy;
- strong distinction between headline performance and diagnostic context;
- restrained but confident use of colour;
- visually integrated filters rather than controls hanging off the page;
- generous but efficient whitespace;
- consistent card geometry;
- clean alignment/grid;
- readable titles/labels;
- clear positive/negative visual semantics;
- trends/comparisons prominent enough to support decision-making;
- minimal decorative noise;
- polished enough to demo without apology.

## Non-goals

Do NOT expand this stage into:

- full conversational user revision;
- all four report pages in the first iteration;
- production multi-tenant auth infrastructure;
- arbitrary real customer data ingestion;
- perfect pixel imitation of generated mockups;
- replacing Power BI native visuals with image overlays;
- direct LLM manipulation of raw PBIR JSON;
- indefinite autonomous visual optimization.

Executive Overview first. Prove quality gain there before generalising.

## Acceptance criteria

- a real reference mockup for Executive Overview is generated using a strong current OpenAI image model;

- the real Fabric Executive Overview is captured automatically;

- no desktop-profile workaround is treated as the target architecture;
- all reference generation, critic, structured revision, and mocked headless components possible without that permission are completed;
- the report specifies the minimum admin/app-registration action required to unblock the live loop.
